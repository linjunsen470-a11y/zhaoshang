# Gemini 审计复核与修复记录

> 历史审计记录：文中的 GitHub 发布开关和 ci-plan 已随发布渠道收敛移除。当前以 [部署说明](ci-deployment.md) 为准。

复核日期：2026-11-01。基准为 `4e8c237` 及当前工作区。核查依据为仓库源码、已安装的 Payload 3.90.2 实现和本地测试；没有把原报告对线上 HTTP、VPS 版本及 GitHub 运行记录的描述当成本次实测结果。

总体判断：多数功能问题属实，适合小改修复；严重度有夸大，媒体权限分析存在明确误判，发布渠道问题需要结合实际运行方式判断。此次没有增加依赖、历史数据兼容层、自动数据修复或新的部署服务。

## 核心问题逐条复核

| 原编号 | 判断 | 证据与处理 |
| --- | --- | --- |
| 1 首页更多服务为空 | 属实，影响三个服务入口；称为 Critical 偏重 | `index.js` 只有 `secondaryServices`，WXML 却循环 `services`。已修正绑定并增加模板契约断言。不能据此断言整个小程序核心功能不可用。 |
| 2 双流水线与发布基线漂移 | 风险属实，但不是必然冲突 | `ci-plan.mjs` 以 GitHub 成功 Deployment 为基线，站外部署不会更新它；存在尚未记录的后端差异时，后续纯文档提交仍可能补发。Gitee 顶层触发器是 manual，不会仅因同步自动与 GitHub 竞争。两边同 SHA 标签相同，且构建源可不同，确有覆盖风险。新增 `CI_BUILD_IMAGES=false` 开关，同时停止 GitHub 镜像/部署和历史基线查询。默认保留现行 GitHub 流程；没有修改远端变量或擅自切换发布渠道。详见 `docs/ci-deployment.md`。所谓“永远滞后”不准确，后续成功 GitHub 发布会推进基线；35 分钟超时不能仅凭源码归因于跨境网络。 |
| 3 自定义后台路由未登录重定向 | 属实，属于页面访问边界问题，不是已证实的数据泄露 | 本地 `@payloadcms/next/dist/views/Root/index.js` 明确排除 custom view 的默认鉴权重定向。已在共享 `AdminWorkspaceShell` 检查用户与 `canAccessAdmin`，不满足时跳转登录。原有 API 员工权限检查保留。未做线上 HTTP 重测。 |
| 4 E2E 与预览脚本失步 | 属实，报告部分字段描述不精确 | 修复旧经营品类必填断言、旧地区选择方法、首页分组及 radio-group 断言；预览详情改用仍有效的 `demo-park`；HTML 预览补载 `lead-form`、`loading` 模板。首页页面字段实际上仍叫 `categories`，内容来自 `options.browseGroups`，不能直接改成读取页面 `browseGroups`。已生成预览数据，但未运行微信原生 E2E，因此不宣称这些 E2E 已通过。 |
| 5 媒体 source=NULL 导致公众读不到 | 核心因果判断错误 | 当前 `@payloadcms/drizzle/dist/queries/parseParams.js` 对非 null 的 `not_equals` 显式生成 `or(isNull(column), ne(column, value))`，并非裸 SQL `<>`。所以不能据此断言空来源图片 403/404。只补 `defaultValue: 'admin'` 使新上传记录来源清晰；不加 `required`，不做非空约束迁移或旧数据回填。 |
| 6 海报面积与费用漏脱敏 | 属实 | 文案已脱敏但 Canvas 仍读原字段。已让 `buildShareMaterial` 返回脱敏后的 `area`、`fee`，绘图复用，并测试已知学校名在这两个字段中的替换。 |
| 7 编辑保存后的重复请求与延迟返回 | 属实 | 四个表单在成功后过早解除锁定且未回收返回定时器。已共用现有 formBehavior 的 `finishEditing`，编辑成功保持锁定，Behavior 销毁时清理定时器。回归测试覆盖四种表单的重复提交阻止与定时器清理。 |
| 8 附件预览返回折叠咨询 | 对发生 onShow 的预览返回路径成立 | 原 `onShow` 会无条件刷新并重建卡片。已在图片预览前标记，返回时跳过一次刷新，打开失败则清除标记；之后普通页面返回仍刷新。通过模拟生命周期回归测试，真机生命周期差异仍需真机检查。 |
| 9 收藏 ID 类型不一致 | 属实 | 新增小型 `isFavorite` 辅助方法，首页、列表、详情与切换收藏统一比较字符串形式。数字数据库 ID 与字符串路由 ID 是当前契约的表示差异，不是历史数据兼容。 |
| 10 表单丢失服务端错误提示 | 属实 | 四个表单展示 `err.message`，缺少消息时保留通用提示，用户可看到限流、项目不可咨询等原因。 |
| 11.1 容器启动与信号 | `exec` 建议合理，启动加速收益未经测量 | 已改成 `exec node server.js`。保留原 libvips 查找，避免为未经证实的启动耗时增加路径假设。`find` 遍历目录元数据并不等于每次读取 156 MB 文件内容；具体 Alpine shell 是否优化末尾命令也不应武断推断。 |
| 11.2 sudo 与磁盘清理 | sudo 不是当前脚本的明确缺陷；保留策略属于运维改进 | `docker login` 无需访问 Docker daemon，且 login/pull 已显式共用同一个临时 `--config` 目录，所以不加 sudo 不等于凭据错位。保留现状，避免引入 root 所有权及清理问题。自动删备份/镜像可能影响恢复，没有擅自新增删除策略；应按容量、异地备份和回退需求另行确定保留周期。 |

## 对验证概览和正面评价的判断

- 原报告的测试数字属于原执行记录，不应继承为本次验证。本次后端 49 项全部通过，包括之前报告受回环端口限制的用例；环境限制不是永久结论。
- 线索输入白名单、附件归属检查、快照冻结、后台与小程序身份分离等主要正面结论与抽查源码一致。“所有安全红线符合”过于绝对，不能由少数单测和代码抽查替代完整安全审计。
- Docker 生产依赖独立层与国内源参数确实存在；具体上传节约量和线上耗时需要真实构建日志，不重复背书未重测的数值。
- 详情相似项目、图片兜底、筛选暂存和手机号授权的实现及测试存在，正面评价合理；原测试没有捕获模板循环字段错误，说明通过测试不代表全部用户路径无误。
