**小程序容量与优化评估（2026-10-29，按日常分散访问调整）**

适用范围：累计数百至数千用户，房源逐步达到数千条，咨询记录随运营持续积累。用户已明确不会有数千人同时使用，因此本方案不以大规模同时在线为设计目标。

结论：保留微信小程序 + Next.js/Payload + PostgreSQL 的现有架构。该业务以筛选、详情展示和咨询登记为主，代码层面未发现必须为数千条房源更换技术栈的理由。最值得先解决的是固定返回上限、后台统计口径、列表查询负担和长列表处理。是否达到具体响应时间仍取决于服务器、数据库、图片大小和网络；本次没有进行生产压测，不提供未经测量的容量承诺。

**1. 已有的有效基础**

- 房源主列表每页 20 条，查询、筛选、排序在服务端执行；并非下载全库后在手机筛选。见 `mp/pages/list/list.js:68`、`backend/app/api/projects/route.ts:20`。
- 首页只请求少量推荐和最新记录；详情页关联铺位也有分页。见 `mp/pages/index/index.js`、`mp/pages/detail/detail.js`。
- 房源公开列表用排序值、创建时间、ID 排序，具有唯一排序末项；同时保留父项目公开状态检查。
- 后台房源与咨询收件箱已有分页。其限制是每页数量，不是全库只能处理 25 条。
- 项目集合声明了场景、录入对象、所属项目索引。不能简单认定项目“完全没有索引”。
- 登录令牌有缓存，客户端合并同时发生的登录请求；咨询接口按用户查询，并保留附件所有权验证。
- 图片上传有大小和格式校验，并进行压缩；设备列表图片已有懒加载。

以上说明这不是必须推倒重来的演示架构。开发环境本地 mock 的数组处理和 `server.js` 也不能当作生产 PostgreSQL 的容量表现。

**3. 第二批：让常用页面稳定、轻快**

**查询与索引。** 仓库中没有看到专门覆盖“用户 OpenID + 创建时间”“咨询状态 + 创建时间”等主要访问路径的业务复合索引声明。生产数据库可能有框架自动索引或手工索引，本次没有连接生产库，不能断言这些索引实际不存在。

在隔离环境核对数据库现有索引和真实 SQL，再用有代表性的数千条数据执行 `EXPLAIN (ANALYZE, BUFFERS)`。优先评估：

| 访问路径 | 候选索引方向（逻辑字段名，不是直接执行的 SQL） |
| --- | --- |
| 我的咨询，按时间倒序 | `submitterOpenId, createdAt DESC, id DESC` |
| 待联系咨询与超时待办 | `status, createdAt, id` |
| 同项目下的铺位列表 | 所属项目字段与实际排序字段组合；先核实已有父项目索引是否够用 |
| 常见区域/场景下的可租房源 | 按最常见筛选组合及排序评估少量复合或部分索引 |
| 公开设备列表 | 公开状态、类型、创建时间组合，视执行计划决定 |

不需要给每个字段都加索引；多列索引的字段顺序、条件选择性和排序方式会影响效果。已有面积、租金两端点索引也不意味着所有区间查询都能快速定位。依据：[PostgreSQL 多列索引说明](https://www.postgresql.org/docs/current/indexes-multicolumn.html)。

Schema 调整遵循仓库要求：先备份，在隔离环境验证后显式执行变更；常规启动继续保持 `PAYLOAD_DB_PUSH=false`。源码中的索引配置和线上实际生效的索引是两件事。

**列表字段。** 房源列表现在使用 `depth: 1` 并调用与详情相同的 `mapProject`，会读取和输出介绍、经营条件、图片列表等详情字段。后台咨询列表同样会读取最终没有展示的部分字段与关系。

建议建立专门的卡片返回结构，保留标题、位置、面积、费用、状态、封面及实际需要的标签，详情点击后再获取。使用查询 `select` 和关联字段选择，减少数据库读取、序列化及手机 `setData` 数据量。不能只把 `depth` 统一改成 0：封面解析、父项目状态和公开内容脱敏仍要正常工作。依据：[Payload Select](https://payloadcms.com/docs/queries/select)。


**客户端算法。** `mp/pages/list/list.js:79` 使用 `filter + findIndex` 对每次合并后的整份列表去重。设当前已加载条数为 m，最坏为 O(m²)。对互不重复的 ID，1000 条要约 500500 次比较，5000 条约 12502500 次；这是代码推导，不是设备耗时测量。

改为 `Set` 或 `Map` 可将单次去重降为预期 O(m)，也可维护已加载 ID 集合，只检查新一页。收藏判断可复用 `Set`。同时注意每次向 `setData` 重传整份列表、持续增加页面节点的成本；先做增量更新，真机发现长列表卡顿后再做分段保留或虚拟列表。数据库有 5000 条，不等于手机需要同时渲染 5000 条。

目前请求序号能防止旧响应覆盖新状态，但不等于取消了后端查询。正常分散访问下不必为此重构请求层；若监测发现频繁切筛选产生明显浪费，再补请求取消和短期结果复用。

**图片。** `backend/collections/Media.ts:87` 只配置本地存储，未配置统一列表缩略图。上传接口虽已压缩，最大输出尺寸仍可达 4096×4096；后台房源图片也没有统一卡片尺寸。

先提供约 480–800 像素的列表缩略图，预览再打开大图，并测量首屏实际下载量。设备公开图片接口每次调用两次 `findByID`、读取本地完整文件，且返回 `Cache-Control: no-store`，这会增加重复浏览成本，但在当前流量预期下不必立刻改造整套媒体架构。见 `backend/app/api/equipments/[id]/images/[mediaId]/route.ts`。

公开房源图片可以根据实测使用浏览器缓存；用户咨询附件以及从咨询中审核公开的设备图片需保留授权、下架和撤回语义，不能直接全部设为长期公共缓存。对象存储/CDN 在磁盘、备份或实际图片流量成为问题时再引入。

**4. 校园业务值得提前修的一处限制**

即使总访问量不高，共用校园或办公室出口 IP 也可能被现有规则误拦：

- 登录：同一 IP 每 10 分钟 30 次，见 `backend/app/api/auth/wechat-login/route.ts:15`。
- 咨询提交：同一 IP 每小时 30 次，同时每用户每小时 10 次，见 `backend/app/api/leads/route.ts:72`。
- 设备图片另有同 IP 每分钟 180 次限制。

建议基于真实日志调整 IP 阈值，让已认证用户维度承担主要约束，IP 作为较宽的兜底；登录仍需保留适当 IP 防护。用多个测试用户共享同一出口的场景验证。无需因此引入 Redis，现有进程内限流在单实例阶段可以继续用；同时确认反向代理正确覆盖来源 IP，避免所有人被识别为同一个代理地址。

**5. 保持简单，延后实施的项目**

| 项目 | 当前决定 | 何时重新评估 |
| --- | --- | --- |
| 微服务、分库分表、读写分离、多实例集群 | 不实施 | 单机优化后，实测仍无法满足业务目标，或有明确高可用要求 |
| Redis 和分布式缓存 | 不作为当前前提 | 确认高重复查询是主要瓶颈，或真正开始多实例部署 |
| 独立搜索引擎 | 不实施 | 搜索数据量、中文分词/同义词需求或延迟确实超出现有数据库能力 |
| 游标分页 | 暂保留现有页码分页 | 深页访问频繁，且执行计划证明偏移扫描成本显著 |
| 消息队列和异步工作集群 | 不实施 | 同步任务频繁超时或明显拖慢前台 |
| 对象存储/CDN | 缩略图之后按需引入 | 实测带宽、媒体增长、备份或运维需要 |

关键词目前是多个字段的 `contains`，并不代表每次必然全表扫描；应先观察实际执行计划。若确有慢查询，可评估 PostgreSQL `pg_trgm`，但短中文词的效果需要实测，不能认为加一个索引就解决所有搜索。依据：[PostgreSQL pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html)。深分页之所以可能变慢，是偏移跳过的行仍需由服务器计算；当前几千条、主要浏览前几页时不必先改造。依据：[PostgreSQL LIMIT/OFFSET](https://www.postgresql.org/docs/current/queries-limit.html)。

腾讯文档同步现在会读取全部咨询和远端记录，逐条比较，写入依次执行；已有哈希及 Map 避免部分重复工作，不能把它描述成纯粹的无优化循环。见 `backend/lib/tencent/sync.ts`。目前可沿用现有单进程脚本，在低峰运行并记录耗时。若后续明显变慢，再按更新时间增量读取、批量提交，并定期全量核对撤回/删除。没有必要现在引入分布式任务系统。

后台一次批量编辑最多 100 条，使用 `Promise.all` 同时读写。后续整理此处时可加小规模并发上限和逐条成功/失败结果，避免数据库请求瞬间堆积以及部分成功后难以判断；不属于当前全站架构重构事项。

**7. 与当前业务相称的验收**

使用隔离数据库和合成资料，准备约 100、1000、5000 条房源，配套父子项目、公开/下架状态、图片和逐步增长的咨询。咨询可能积累得比房源快，可以追加一组数万条历史咨询验证筛选；这只是测试数据量，不代表需要数万人同时在线。

访问测试从单用户完整流程开始，再用 5–10 个模拟用户带正常停顿的混合浏览作冒烟验证。这个数量只是初始测试设置，后续以实际峰值修正；不做千人同时在线场景。

重点验收：

- 第 101 条设备能通过翻页找到；个人咨询超过 100 条仍完整；静态数据分页没有重复、遗漏，同创建时间记录有明确 ID 排序。
- 500 条以后仍纳入质检统计；较早房源能搜索并生成分享素材；若保留旧统计，超过 1000 条后数字仍准确。
- 查询首屏、典型组合筛选、关键词、详情和个人咨询的响应耗时，记录 P50/P95 及 SQL 执行计划；区分首次启动与热请求。
- 可先把普通热查询 API 的 P95 ≤ 500ms、代表性手机网络首屏可用 ≤ 2s 作为讨论用目标，需结合部署地区和网络基线确认；这是拟定验收标准，不是本次测得成绩。
- 真机连续翻多页，检查弱网、图片加载、返回列表、收藏、提交重试及错误提示。加载几千条数据不是手机必须完成的日常操作。
- 多个账号共享 IP 时不会在正常使用下被过早限流；限制对异常重复提交仍有效。
- 在测试环境验证请求成功但响应丢失后重试的行为；若会重复创建咨询，后续增加提交幂等键，不依赖前端按钮禁用来保证唯一性。
- 在单实例条件下确认数据库连接池等待、内存、上传处理时间与磁盘增长保持可控；连接数按数据库实际预算设置，不能仅靠盲目增大池大小。
